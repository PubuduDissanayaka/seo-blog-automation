# Architecture and Astro Implementation

## Step 1 - Evaluate requirements, then pick the stack

Do not default to the reference stack blindly and do not over-build. Answer these before writing code:

1. Content shape: articles with authors/categories/images? Static data? External CMS or API content?
2. Publishing model: who writes, how content enters the site, how often.
3. Interactivity needs: search, forms, filtering, user accounts, comments?
4. Scale: how many pages now and in a year.
5. Budget: must run free or near-free.

**Default recommendation (matches MyGreenyGarden):** Astro static output + TypeScript + content collections
(glob loader) + markdown/MDX + Tailwind + Cloudflare Pages git-connected + GitHub. This gives zero-JS HTML
by default, build-time validation, free hosting, and deploys on push.

**Escalate only when justified:**
- A form/lead endpoint or a small dynamic bit -> a single Cloudflare Pages Function or Worker route, not a
database.
- User accounts, real-time data, a search index too large for client-side -> reconsider the platform
before adding a database. State the requirement that forced it.
- SSR/ISR -> only for per-user or frequently-changing content; a content blog almost never needs it.

Never add a database, an auth system, or a framework "because you can". State each architectural decision
and its reason in PROJECT.md.

## Rendering strategy

Static generation (SSG) is the default. HTML rendered at build time is the fastest, cheapest and most
crawl-stable option for a content site. Use SSR/Workers/dynamic code only when a concrete requirement
demands it, and say which one.

## Astro architecture

Follow `astro-static-site-build` for the exact scaffold, token layer, motion rules and verification
templates - it owns the pitfalls that ship blank pages. Summary of the structure it uses:

- `astro.config.mjs`: `site` (the ONE place the origin is declared), `trailingSlash: 'always'`,
  `build.format: 'directory'`, `integrations: [sitemap(), mdx()]`.
- `src/content.config.ts` (Astro 5 content layer): `defineCollection({ loader: glob(...), schema })` with
  strict zod schemas that fail the build on a bad field.
- `src/data/site.ts`: every repeated string and destination (nav, footer, site name, tagline, analytics
  id, adsense publisher id). One edit changes it everywhere.
- `src/data/head.ts`: the typed head inventory (meta/links/scripts) with `env`, `load`, `consent` fields so
  a prod-only or consent-gated tag cannot leak across builds.
- `BaseLayout.astro` + `Header` + `Footer` + section components; per-page JSON-LD stays with the page that
  owns it.
- `src/pages/robots.txt.ts`: generate robots.txt from `site`, never commit it as a static file.
- `src/pages/404.astro`: custom 404 that Pages serves with a real 404 status.

Content collections: read the real frontmatter before writing a category enum (artboard tabs are
placeholders, not the taxonomy). `image()` is the schema-context function, resolves relative to the entry
file, needs `sharp`. `entry.body` is `string | undefined`; pass `entry.body ?? ''` to helpers. Keep
drafts out of both the build and the sitemap via the page's `getStaticPaths` filter.

## Page architecture (build only what the business needs)

Evaluate each and create it only when the business model, target region or publishing needs demand it:

- **Home page** - latest content, categories, brand.
- **Blog index** - all articles with pagination.
- **Category pages** - one per top-level category, with unique intro copy (never a thin archive).
- **Article pages** - `[slug].astro`, the core template.
- **Author pages** - needed for E-E-A-T; one per real author with bio and credentials.
- **About** - real people, real purpose; required for AdSense trust.
- **Contact** - working route; required for AdSense.
- **Privacy policy** - required, substantial, names cookies and vendors.
- **Terms, Editorial policy, Affiliate disclosure, Advertising disclosure, Cookie/consent info** - as
  required by region and monetisation.
- **Search** - Pagefind for a static site; see `astro-static-site-build` references/pagefind.md for the
  CSP directive (`wasm-unsafe-eval`) and payload budget.
- **Sitemap** - generated by `@astrojs/sitemap`; submit the INDEX.
- **Custom 404** - always.

Do not create thin pages to fill a list. A sub-topic with no measured demand becomes a section inside a
parent page, not its own route.

## URL structure

- Readable, lowercase, hyphenated slugs derived from the title, with the primary keyword when it reads
  naturally.
- Consistent slug convention across all content; no dates in URLs for evergreen content.
- Category structure: `/blog/<slug>/` or `/category/<name>/` - pick one, document it, never mix.
- URL changes always ship a 301 in `_redirects` to the new location.
- Prevent duplicate URLs: one canonical form per page, `trailingSlash: 'always'`, no query-string variants
  indexed.

## TypeScript and coding standards

TypeScript where it earns its keep (schemas, data modules, `getStaticPaths`). Extend
`astro/tsconfigs/strict`. Prefer `node:test` for `src/lib` helpers (no extra test framework). Avoid
unnecessary client-side JS; keep interactions progressive-enhancement (native `popover`, `<details>`, CSS
scroll animations per `modern-web-guidance`). No large dependencies for small functionality. Handle build
errors with clear messages; make every build reproducible (`npm ci`, locked lockfile).

## Search

Pagefind is the proven choice for static Astro blogs. Wire the post-build index and the Component UI, style
through `--pf-*`, scope with `data-pagefind-body`, and remember the `wasm-unsafe-eval` CSP directive or
the engine hangs. Details: `astro-static-site-build` references/pagefind.md.
